# CLAUDE.md

## General Rules & Code Style
- **Imports:** ALWAYS use absolute imports (`@/` in the Angular apps) instead of relative paths (`../`, `./`).
- **Architecture:**
  - **Go services (`services/`):** Follow standard Gin conventions, not Clean Architecture — `cmd/<service>/main.go`, and under `internal/`: `config`, `routes` (router + middleware wiring), `handlers`, `middleware`, plus domain packages as needed. Shared code lives in `services/pkg`.
  - **Angular apps:** folders by role and area, not Feature-Sliced Design — see Angular Apps → Layout.
- **Formatting & Linting:** Use **Biome** for formatting and linting (`pnpm exec biome check --write`); Angular templates are linted with `angular-eslint` (`ng lint`).
- **Validation:** go-playground/validator in the Go services (via `services/pkg/validation`), **Signal Forms** (+ Zod schemas via Standard Schema) in the Angular apps.
- **Logging:** `log/slog` in Go. Avoid `console.log`.
- **Environment:** Manage environment variables via `dotenv` (`.env`).
- **TypeScript:** Strict mode enabled. Always specify return types for public functions/methods.
- **Git:** Claude may commit and push straight to `main`, without a branch or PR. Before pushing, run the checks for what changed (Biome, `ng lint`, `pnpm typecheck`, the app's tests; `golangci-lint` and `go test ./...` for a Go module), and say so if one fails. A push to `main` deploys staging (`deploy-staging.yml`).

**Track B — Telegram bot, NestJS + Telegraf → Go + [Telego](https://github.com/mymmrac/telego) (`services/bot`): done** (the NestJS `apps/bot` is removed).

Layout: `cmd/bot/main.go`, `internal/{config,handlers,keyboards,screens,session,users,api,store,migrations,blogfeed}`.
- Long polling; users data over the `users` gRPC API (`BOT_TOKEN`, `USERS_GRPC_ADDR`, `MINI_APP_URL`).
- Sections (design: the "Ermekten — Telegram-бот" canvas): 🎒 my tours (the tours the user signed up for, upcoming and past; a tour's card with signing up and cancelling — `o:` callbacks, `screens/trips.go`), 🧭 tours (favorites, upcoming, new-tour alerts, the description read in the chat, with «✋ Записаться»), 📰 blog (posts read in the chat, paged), 🔔 notification settings. Outings were merged into tours and are gone from the bot; old draft (`d:`) and condition-report (`c:`) buttons only say they are out of date. 🧑‍✈️ The organizer's room (`/organizer`, from «Мои туры» and the organizer's card; `g:` callbacks, `handlers/organizer.go`): the partner's tours (`/tours/mine`) — the roster with links to participants' Telegram, marking arrivals (`listings`: `PUT|DELETE /tours/:id/participants/:userId/arrival`, from a day before the meeting to a week after; the organizer's reminder carries `g:rn:<tour>`), a message to all participants, program by day, 30-day stats, paid bookings. ⭐ After a tour participants rate it in the chat (`r:` callbacks, `handlers/rating.go`; `listings`: `PUT /tours/:id/rating`, only those marked on arrival once the organizer marks anyone): the rating is their review of the tour (`reviews`), shown on the tour's and the organizer's pages. They call the gateway (`API_URL`) as the user, with a short session signed with `JWT_SECRET` (`internal/api`) — off without both. A section is one message: inline buttons edit it (`internal/screens` renders text + keyboard; site HTML becomes Telegram HTML in `screens/richtext.go`). Covers show as a link preview above the text (`PUBLIC_API_URL` for `/uploads/…`). `screens/sketches_test.go` renders every artboard from its data: change a screen and its sketch together.
- **Languages, as on the site (ru, ky, en, de):** `internal/i18n` — texts are written in Russian in the code (`l.T("…")`, `l.F(format, …)`, plurals `l.N(n, one, few, many)`, dates `l.When`/`l.DateRange`…) and translated in `internal/i18n/locales/{ky,en,de}.json`, keyed by the Russian text. `catalog_test.go` fails on any Russian string in the code without all three translations (or with mismatched `%` verbs / HTML tags), and `screens/languages_test.go` renders every screen in English to catch a text left untranslated: a new or changed text needs its catalog entries. A chat's language is kept in the bot's database (`chat_languages`): taken from the Telegram app's language the first time, changed with `/language` or from the profile; main menu buttons are matched in every language, the Mini App opens the site under the language prefix, tours and blog posts come in the chat's locale, the blog feed sends each language's posts to its readers. The bot reports each chat's language to `users` (`SetTelegramLanguage`, table `telegram_languages`, keyed by Telegram id; `users.Languages` wraps the store: once per chat per run and on every change), and `GetTelegramChats` returns it with the chat id (`usersclient.TelegramRecipients`), so notifications from `listings` (`internal/notify`, `internal/alerts`) come in the recipient's language too: Russian texts in the code, translated in each package's `locales/{ky,en,de}.json` through `pkg/telegram` (`Catalog.T`/`F`, `Lang.When`), worded as in the bot's catalogs; callback data doesn't change with the language. `payments` notifications are still Russian.
- **Everything is done in the chat:** no section button opens the Mini App or the site; only the main menu's "🏔 Открыть Ermekten" (and the chat menu button) open the Mini App. Notifications from `listings` carry callback data the bot answers (`o:view:n:<tour>`, `g:rn:<tour>`, `r:s:<tour>`, `t:open:<tour>`; `pkg/telegram.Button.Data`), not site links. Sharing a tour uses Telegram's share dialog with the bot's `tour_<id>` deep link.
- Its own database (`BOT_DB_NAME`): blog subscribers and posts already sent; `internal/blogfeed` checks the blog every 10 min and sends new posts. Deep link `tour_<id>` opens a tour's card.
- Account linking and the profile keep the NestJS bot's deep links (`verify_`, `link_`), callback data and texts. Bot changes go to `services/bot` only.
- `listings`/`payments` keep sending notifications through `services/pkg/telegram`.

## Angular Apps
- **Stack:** Angular 22 standalone components, zoneless, `OnPush`, signals (`signal`/`computed`/`input`/`output`/`model`), `inject()`, built-in control flow (`@if`/`@for`/`@defer`), `HttpClient` (fetch) with `httpResource`/`resource`, Signal Forms with `zod/mini` schemas (`validateStandardSchema`; the full `zod` build adds ~70 kB gzipped to the browser), Transloco (`src/locales/*.json`, one lazy chunk per language; `{param}` interpolation), Tailwind CSS 4 + Iconify (`icon-[heroicons--map]`), design tokens from `packages/tokens`, Angular CDK/Aria under the in-house `ui/` kit, Vitest. Node from `.nvmrc` (`nvm use`; Angular CLI 22 needs ≥ 24.15).
- **Layout:** `src/app` (bootstrap, config, `app.routes.ts`, `app.routes.server.ts`, root component); `src/core` (app-wide services and helpers by topic: `api`, `config`, `auth`, `i18n`, `seo`, `lib`…); `src/layout` (the page frame: header, footer, sidebar and their controls); `src/ui` (reusable components and directives); `src/pages/<area>` (route components plus anything only that area uses). Dependencies point inward: `pages` → `layout`/`ui` → `core`; `core` and `ui` never import `pages`. Move something to `ui`/`core` once a second area needs it.
- **Runtime config, not build-time:** one image serves every environment. `apps/site` reads `API_BASE_URL`, `SITE_URL`, `TELEGRAM_BOT_USERNAME` (and the server-only `API_INTERNAL_URL`, the gateway on the Docker network for server-side requests) in `src/server.ts` and hands them to the app via the request context + TransferState (`APP_CONFIG`); `apps/panel` loads `/config.json`, written from `API_BASE_URL` when its nginx container starts.
- **Data and forms:** read with `httpResource` (reactive URL, `reload()` after a change), write with `HttpClient`; custom form controls implement `FormValueControl` (`value = model()`), and limits like max length go into the form schema (`maxLength`, `min`), not template attributes. Uploaded images (`/uploads/…`, the R2 bucket) render with `NgOptimizedImage` and a `sizes` in `vw` (no `px`: NG02952): the app's loader (`core/lib/image-loader.ts`) turns them into a `srcset` of thumbnails from `services/media` (`GET /images/<width>/{uploads|r2}/…`, made on first request and cached on the uploads volume; widths in `IMAGE_WIDTHS` = `imageconv.ThumbnailWidths`). Icons whose names come from the API (`i-mdi-trophy`) render through `app-icon` (Iconify web component); static ones use the CSS classes.
- **Admin history and partners (`apps/panel`):** every successful POST/PUT/PATCH/DELETE made with an admin session is recorded by `services/pkg/audit` (middleware in users, content, trails, payments; table `admin_history` in each service's own database; `routes.HistoryModules` maps path prefixes to panel modules; request bodies kept with secrets hidden and long strings cut; `audit.SetSubject` names what changed when the body doesn't). The panel reads it per module (`GET /<prefix>/admin/history?before=&limit=&entityId=`, `core/history`, `ui/history-log.ts` at the bottom of each section) and all together on `/history`. Partners (`/partners`): applications, partners and rejected; `GET|POST /partners`, `PUT|DELETE /partners/:userId` (users service) add an existing account as a partner, change kind/status/contacts, or take partnership away (the account stays).
- **apps/panel UI kit:** `ui-*` classes in `src/styles.css` (buttons, fields, tables, badges, dialogs), dialogs via Angular CDK `Dialog`, `src/ui` for the image upload field, the Tiptap editor and icons.
- **Rendering (`apps/site`):** set every route's mode in `app.routes.server.ts` — `RenderMode.Server` for public catalog and detail pages (anonymous render, cacheable HTML), `RenderMode.Prerender` for static pages, `RenderMode.Client` + `noindex` for account, cabinet, payment and edit pages (list them in `CLIENT_PATHS`: their shell goes out with `X-Robots-Tag: noindex`, since the page's own meta tag needs JavaScript). `sitemap.xml` (an index of `/sitemaps/<type>.xml`, `src/server/sitemap.ts` — add new content types there) and `robots.txt` are served by the SSR server.
- **Links (`apps/site`):** internal links use `appSiteLink="/tours"` (`ui/site-link.ts`), which adds the language prefix and routes inside the app; `injectSiteNavigate()` (`core/lib/site-navigate.ts`) does the same from code. Session state comes from `core/auth/auth.store.ts` (`AuthStore.ensureSession()`, browser only); `requireAuth`/`requirePartner` guard Client-rendered routes.
- **Motion (`apps/site`):** durations `--dur-*` and easings `--ease-*` (Tailwind `ease-spring`…) in `packages/tokens`; shared classes in `src/motion.css` (`motion-lift` cards, `motion-reveal` lists rising into view, `ui-skeleton`, `icon-anim-*` / `icon-swap` icons, `motion-roll-in` for `animate.enter`). Pages change with View Transitions (`withViewTransitions` in `app.config.ts`; query-only changes skip it); `ui/shared-transition.ts` names an element that flies to the next page. Animate only `transform`/`opacity`, and give everything a `prefers-reduced-motion` fallback (a short fade or nothing).
- **Notifications and states (`apps/site`):** toasts through `Notify` (`core/notify/notify.ts`, shown by `layout/toast-outlet.ts`; translation keys, never raw text), confirmations through `injectConfirm()` (`ui/confirm-dialog.ts`, never `window.confirm`), empty/error/success blocks through `ui/state-block.ts`, bottom sheets through `ui/bottom-sheet.ts`. A page asks the frame for a see-through header, its own bottom bar or no header on phones via `usePageChrome()` (`core/lib/page-chrome.ts`). Design reference: `docs/design/ermekten-ui-sketches.pdf`.
- **Online payments (`payments`, `apps/panel`):** the gateway is `PAYMENTS_PROVIDER` — `gopay` ([GoPay](https://doc.gopay.kg/v1/), ELQR: `provider/gopay.go`), `bakai`, `fake` (a test page) or `off`. GoPay has one host (`GOPAY_API_URL`); the key pair picks the mode: Test keys on staging (no money moves; the amount picks the outcome — 200.00 cancelled, 300.00 expired, 400.00 failed, else paid), Live keys in production — `GOPAY_API_KEY`, `GOPAY_SECRET_KEY`, `GOPAY_WEBHOOK_SECRET` as each GitHub environment's secrets, never in the code. Requests and webhooks are signed HMAC-SHA512 (`nonce\nbody\n`, uppercase hex); GoPay's `order_id` is the order's uuid without dashes (32 chars max). Its `events_url` (dashboard → Developer → Webhooks: `payment.committed/.failed/.expired/.cancelled`) is `<API>/payments/gopay/events`: a delivery with a valid signature only triggers a status query (`worker.Check`), deliveries are kept in `provider_events` (a processed `event:payment_id` is skipped), and the worker still polls pending orders. GoPay's record of each payment is `provider_payments`. GoPay has no refund API: the admin cancels an unpaid payment (`/v1/payments/cancel`) and marks a refund made in GoPay's dashboard (`POST /orders/:id/refund`). The panel's `/online-payments` (list with status and date filters, a payment's card: check at GoPay, cancel, refund, webhook log) reads `GET /payments/admin/gateway|transactions[/:id]`, `POST …/:id/check|cancel`. Booking on the site stays paused until the user asks.
- **Paused sections (`apps/site`):** hotels, local guides, travel guides and online booking/payments are off for now (the focus is tours): their pages, links and sitemaps are removed, and their addresses redirect with 302 (`src/server/paused-sections.ts`). To bring them back, revert the commit that removed them and drop their entries there. Outings are gone for good (merged into tours): `/outings/**` redirects to `/tours` with 301 (`MOVED_SECTIONS` there).
- **Signing up for tours (`apps/site`, `listings`):** a tour is one departure (`startDate`–`endDate`, `capacity` places, optional `meetingPoint` and `meetingTime` HH:MM in Bishkek, 09:00 when unset). Sign-up stays open until the tour is over (the evening of its last day, 18:00 Bishkek — `EndsAt`), so a late traveler can still join after the group met. Travelers sign up on the tour page (`pages/tours/tour-signup.ts`, read in the browser from `GET /tours/by-id/:id`: `isJoined`, `isOrganizer`, the organizer's `roster`, `canRate`/`myRating`) and in the bot: `POST|DELETE /tours/:id/join`, `GET /tours/joined` (the profile's history). Only partners create tours. `listings/internal/notify` (an outbox table and a worker, on with `BOT_TOKEN`) tells the organizer about sign-ups, participants about a moved or deleted tour, both a reminder 12 h before the meeting, and participants a request to rate it after.
- **Partner CRM and chats (`apps/site`, `listings`):** `/partner/clients` (the client base: accounts that signed up for the partner's tours — `crm_clients`, added on sign-up — and people added by hand, with notes and tags), `/partner/tours/:id/participants` (the group: statuses `new`/`confirmed`/`waitlist`/`cancelled`, check-in, what each owes — `amountDue` or the price — and payments received by hand; CSV export), CRM tiles on `/partner` (`GET /crm/summary`); API `/crm/*`, partners only. A participant is an account (`user_id`) or a client added by hand (`client_id`); only `new`/`confirmed` take a place — a full tour puts travelers on the waitlist and a freed place goes to the first on it (`store.promote`, told in Telegram). Roster, reminders and ratings count accounts with a place only. The participant's form (emergency contact, mountain experience, health — `ui/participant-form.ts`) and the rules and risks they accept (`waiver.v1.*` in the locales = `models.WaiverVersion`; a changed text gets a new version) come with the sign-up on the site (`POST /tours/:id/join` with `form`, `acceptWaiver`; the bot signs up without a body), or later (`PUT /tours/:id/form`); the partner sees them in the group and fills one in for a client added by hand (`PUT /crm/tours/:id/participants/:pid/form`). Only the participant and the tour's organizer see a form. Also in the cabinet (plan and status: `docs/crm-roadmap.md`): leads (`/partner/leads`, `crm_leads` — a traveler's first message to an organizer opens one, `store.OpenInquiry`; signing up wins it, `winLeads`), tasks (`/partner/tasks`, on the dashboard and the client card), a tour's expenses and staff with the margin (`app-tour-ops` on the group page), refunds (`tour_payments.kind`), a client's source, message templates and broadcasts (`/partner/broadcasts`: into each client's chat), reports (`/partner/reports`, `GET /crm/reports?from=&to=`). Chats (`/chats/*`, tables `chats`, `chat_messages`): partners write to their clients (with an account), travelers to organizers of published tours (`/messages`, «Написать организатору» on the tour page); the site polls (5 s in an open chat, the unread badge every 30 s — `core/chat/chats.ts`), and `listings/internal/notify` tells the other side in Telegram at most once per 10 min per chat, with a URL button to the chat on the site (`SITE_URL`).
- **Drivers (`apps/site`, `listings`, `users`):** a partner is a tour organizer or a driver (`users.partner_kind`, chosen in the profile's partner tab: `POST /partners/apply` with `kind`; in the session lookup and the gRPC user as `PartnerKind`; `middleware.RequireOrganizer`/`RequireDriver`). Only organizers create tours. A driver's cabinet is `/partner` with its own pages (`pages/partner/driver`, routes matched by `matchDriver`): the dashboard (requests, next trips, money this month, vehicle documents running out within 30 days), trips (`/partner/trips`, `driver_trips`: an organizer's request for a tour — `requested` until the driver accepts or declines — or one they write down; payments and costs per trip), vehicles (`/partner/fleet`), costs (`/partner/costs`), earnings (`/partner/earnings`) and their card in the organizers' catalog (`/partner/driver-profile`, `driver_profiles.published`); clients, tasks, templates, broadcasts and chats are the shared `/crm/*` ones (an organizer who asks for transport becomes the driver's client). API `/driver/*` (drivers only). Organizers find drivers on a tour's group page (`app-tour-transport`: `GET /crm/drivers?date=&seats=`, `POST /crm/tours/:id/transport`, `DELETE /crm/transport/:id`) and can write to a published driver; both sides hear about requests and answers in Telegram with a link to the site. The driver sees the tour's dates, meeting point and group size, not participants' names.
- **Password reset (`apps/site`, `users`):** «Забыли пароль?» on `/login` asks `POST /auth/user/password/forgot` (`identifier`, `channel` email|telegram, `lang`) for a one-time link to `/reset-password#<token>` (RenderMode.Client; the token is in the fragment and dropped from the URL once read), sent by Resend or, for a linked Telegram, by `users` itself through `pkg/telegram` in the chat's language (`users/internal/resetmsg`). Tokens are stored as sha256 (`password_reset_tokens`, 30 min, one use); requests are limited per typed identifier and IP (`password_reset_requests`) with the same answer for unknown accounts, and delivery runs after the answer. `POST /auth/user/password/reset` (`token`, `password`) sets `users.sessions_valid_after`: the auth middleware (`RequireUser`, and `OptionalUser` with a lookup) refuses sessions whose `iat` is older (`GetUser` returns it).
- **Organizer pages (`apps/site`):** `/organizers/:id` — profile and «Проверенный» badge (an approved partner) from `users` (`GET /users/:id/public`), tours held, participants, upcoming tours, reviews and replies from `listings` (`GET /tours/organizers/:userId?locale=`). Linked from the tour pages.
- **Legal documents (`apps/site`):** `/offer`, `/privacy`, `/refunds` — registry in `core/legal/documents.ts` (a `draft` page shows a notice, is `noindex` and stays out of the sitemap), the operator's requisites in `core/legal/company.ts`, the Russian texts in `pages/legal/texts` (other languages show them with a note). Linked from the footer, the sign-up form and the booking form.
- **Page states (`apps/site`):** an unknown slug renders `NotFoundPage` (status 404); a failed API call renders `ui/load-error` (status 503 via `core/seo/response-status.ts`, which nginx doesn't cache). Browser-only routes (RenderMode.Client) get their runtime config from `/app-config.json`, served by the SSR server.
- **SSR safety:** no `window`/`document`/`localStorage`/Telegram WebApp access outside `afterNextRender`, `@defer` or an `isPlatformBrowser` check. Server-rendered data reaches the client through the HTTP transfer cache — never fetch it twice. That data is the anonymous view (the server sends no cookies): per-user fields (`isJoined`, own bookings) must be re-fetched in the browser after hydration (with `transferCache: false` when it's the same URL, or the cache hands back the server's anonymous answer).
- **SEO on every public page** (through `core/seo`): title and description (admin `/page-seo` overrides win), absolute canonical, `hreflang` for all locales + `x-default`, Open Graph/Twitter, JSON-LD for the page type plus `BreadcrumbList`, correct HTTP status (404 for unknown slugs), `NgOptimizedImage` with dimensions and an LCP `priority` image, heavy widgets (maps, reviews, booking, charts, editor) behind `@defer` with incremental hydration — `hydrate on viewport`/`idle` for anything that depends on the signed-in visitor (never `on interaction`: until then the server's anonymous HTML stays, and the click is replayed on it). Deferred components need a box of their own (`host: { class: 'block' }`) for the viewport trigger.

## Analytics (Firebase / GA4)
- **One GA4 property** (the Firebase project's), one web data stream; off wherever its env is unset. Events keep the same names in the site and the bot where they mean the same thing (`view_tour`, `join_tour`, `leave_tour`…), and every event carries the language as `lang`.
- **Site (`apps/site`, `core/analytics`):** Firebase Analytics in the browser only, from the runtime config (`FIREBASE_API_KEY`, `FIREBASE_PROJECT_ID`, `FIREBASE_WEB_APP_ID`, `FIREBASE_MEASUREMENT_ID` → `APP_CONFIG.firebase`, null unless all four are set). Nothing loads before the visitor answers «Разрешить» in the cookie notice (`layout/cookie-consent.ts`, `CookieConsentStore`; «Настройки cookie» in the footer asks again; a refusal stops collection and drops the `_ga*` cookies); the SDK is its own lazy chunk. `Analytics.track(name, params)` with names typed in `AnalyticsEvents`, `trackItemView()` for a detail page; page views are sent by the site on each navigation once the page is stable (`content_path` is the path without the language prefix). A new kind of data collected goes into the privacy policy (`pages/legal/texts/privacy.ts`).
- **Bot (`services/bot`, `internal/analytics`):** the GA4 Measurement Protocol to the same web stream (`FIREBASE_MEASUREMENT_ID` + `GA_API_SECRET`, the stream's Measurement Protocol secret), queued and sent in the background (`Client.Track` never blocks; a full queue drops the event). A chat is `client_id`/`user_id` = HMAC-SHA256 of its id keyed with `ANALYTICS_SALT`. Handlers report through `h.track` (`handlers/analytics.go`): `bot_start` (`deep_link`: verify/link/tour/other/none — never the token), `menu_select` (`section`), `join_tour`/`leave_tour`, `language_change`, `view_tour` (`source`: list/alert), `view_article`.

## Go Services
- **Stack:** Go (version in each `go.mod`), Gin, `log/slog` JSON logging (`services/pkg/logger`), `go-playground/validator` via Gin binding, config from env via `services/pkg/config` (`.env` supported).
- **API contract:** The frontend apps depend on the existing paths, cookies (`user_token`, `admin_token`), JSON shapes and NestJS-style error bodies (`services/pkg/httperr`, zod-style validation errors from `services/pkg/validation`). Keep them stable.
- **Lint/Test:** `golangci-lint run ./...` per module (config in `services/.golangci.yml`), `go test ./...`. Imports: stdlib, third-party, then `github.com/elvn5/sai/...`.
- **Databases:** Each service owns its own PostgreSQL database (created on first start), with goose SQL migrations embedded from `internal/migrations` and pgx for queries. No cross-database foreign keys — reference other services' records by id.
- **Inter-service calls:** gRPC; contracts in `services/proto` (buf). Run `pnpm proto:generate` after editing a `.proto` and commit the generated code.
- **Modules:** One Go module per service; local `pkg` is wired with a `replace` directive so each service builds alone (`GOWORK=off`) in Docker.

## Tech Stack
- **Backend:** Go + Gin (`services/`), gRPC (buf), PostgreSQL (pgx, goose), Docker
- **Bot:** Go + Telego (`services/bot`), long polling, gRPC client to the users service, the gateway on users' behalf, its own PostgreSQL database
- **Frontend:** Angular 22 + `@angular/ssr` (`apps/site`, `apps/panel`) — see Angular Apps above
- **Linter/Formatter:** Biome (+ angular-eslint for Angular templates)
