# Миграция: фронтенд с Nuxt 3 на Angular 22, Telegram-бот на Go

Статус: трек А завершён (фазы 0–7, 16.10.2026); трек Б — до шага Б5. План составлен по коду на 14.10.2026 (`main` после PR #59).

Два независимых трека:
- **Трек А — фронтенд:** Nuxt 3 → Angular 22 (разделы 1–8).
- **Трек Б — бот:** NestJS + Telegraf → отдельный Go-сервис в своём Docker-контейнере на фреймворке Telego (раздел 9).

## 1. Зачем и чего это стоит

**Что мигрируем:**

| Приложение | Сейчас | Объём | Станет |
|---|---|---|---|
| Публичный сайт + Telegram Mini App | `apps/tourism` (Nuxt 3, SSR) | 41 страница, 47 компонентов, ~12,8 тыс. строк, 4 языка | `apps/site` (Angular 22, SSR + SSG) |
| Админка | `apps/admin` (Nuxt 3) | 11 страниц, ~1,9 тыс. строк | `apps/panel` (Angular 22, только клиент) |

Go-сервисы и API-контракт (пути, cookie `user_token`/`admin_token`, JSON) не меняются. Бот переезжает отдельным треком (раздел 9).

**Важно понимать заранее.** Nuxt уже умеет SSR и SSG, поэтому сама смена фреймворка SEO не улучшит. Улучшат его требования из раздела 4. Часть из них сейчас не выполнена, и это можно сделать и в Nuxt:

- нет JSON-LD у туров, гидов и маршрутов;
- в sitemap нет маршрутов и выходов и нет `hreflang`;
- отрендеренные страницы не кешируются;
- каталоги листаются кнопкой «Показать ещё» без ссылок, по которым может пройти поисковый робот.

В этом плане они заложены в критерии готовности каждой волны, чтобы новый сайт был не просто равен старому, а лучше него.

**Цена:** две кодовые базы на время миграции. Для крупных фич действует правило из раздела 6.

## 2. Целевой стек

| Задача | Nuxt сейчас | Angular 22 |
|---|---|---|
| Рендеринг | Nuxt SSR | `@angular/ssr`, режим рендеринга задаётся для каждого маршрута (`RenderMode.Server` / `Prerender` / `Client`), инкрементальная гидрация (`@defer (hydrate on …)`), повтор событий, совершённых до гидрации (event replay) |
| Реактивность | Vue refs | Сигналы, без zone.js (zoneless), `OnPush` |
| Загрузка данных | `@tanstack/vue-query` + перенос состояния с сервера на клиент | `HttpClient` на fetch + `httpResource`/`resource`, кеш переноса с сервера на клиент (`withHttpTransferCacheOptions`), чтобы клиент не запрашивал заново то, что уже отрендерил сервер |
| Состояние | Pinia (+ persistedstate) | Сервисы на сигналах; `localStorage` только для удобств конкретного пользователя |
| Формы | VeeValidate + Zod | Signal Forms (стабильны в v22); существующие Zod-схемы переиспользуем через Standard Schema |
| i18n | `@nuxtjs/i18n`, `prefix_except_default` | Transloco: текущие `ru/ky/en/de.json` берём как есть, язык определяется по первому сегменту URL |
| UI | `@nuxt/ui` 2 + Tailwind 3 | Tailwind 4 + собственный набор компонентов в `ui/` на базе Angular CDK / Angular Aria; дизайн-токены из `tokens.css` переносим |
| Иконки | Nuxt Icon (`i-heroicons-*`, `i-mdi-*`) | Iconify через плагин Tailwind: иконки отдаются как CSS, без JS и без лишнего кода для SSR |
| Редактор, карта, QR | Tiptap Vue, Leaflet, `uqr` | Ядро Tiptap + обёртка, Leaflet и `uqr` как есть; всё это только в браузере, внутри `@defer` |
| Сборка и тесты | Nuxt / Vite | Angular CLI (`@angular/build`), Vitest |
| Линт и формат | Biome | Biome для TS/JSON/CSS, `angular-eslint` для шаблонов (Biome их не проверяет) |
| Архитектура | FSD в `components/{entities,features,widgets,shared}` | Без FSD: `src/{app,core,layout,ui,pages}` — по роли и разделу, импорты через `@/` |

Почему Transloco, а не встроенный `@angular/localize`. Встроенный i18n собирает отдельный бандл на каждый язык, требует переписать ~700 ключей в шаблоны и формат XLIFF и усложняет схему «русский без префикса». Transloco использует существующие JSON-файлы без изменений и даёт одну SSR-сборку. Совместимость с Angular 22 проверяем в фазе 0, до написания страниц.

## 3. Рендеринг по маршрутам

Схема URL не меняется: русский без префикса, `/ky`, `/en`, `/de`. Это главное условие, чтобы сохранить позиции в поиске.

| Маршруты | Режим | Почему |
|---|---|---|
| `/`, `/tours`, `/hotels`, `/local-guides`, `/trails`, `/outings`, `/blog`, `/guides`, `/gallery`, `/hall-of-fame` и их детальные страницы | **SSR** + кеш HTML в nginx (`s-maxage` ~5 мин + `stale-while-revalidate`) | Контент меняется из админки без пересборки; кеш даёт скорость статики, а данные остаются свежими |
| Статичные страницы: оферта, политика конфиденциальности, правила возврата, «о проекте» | **SSG** (`RenderMode.Prerender`) | Не зависят от API |
| `/login`, `/profile`, `/partner/**`, `/payments/**`, все `*/new` и `*/edit`, `/achievements/award` | **Client** + `noindex` | Личные страницы; на сервере их рендерить незачем, и они не попадают в кеш |
| Вся админка | **Client** | Не индексируется |

Публичные страницы на сервере рендерятся без пользователя: cookie не пробрасываются, поэтому HTML одинаков для всех и его можно кешировать. Персональное (аватар в шапке, «моя бронь», кнопка кабинета) догружается в браузере.

## 4. Требования к SEO: критерии готовности каждой публичной страницы

**Мета и разметка**
- [ ] `<title>` по шаблону `{страница} — Ermekten`, уникальный `description`. Переопределения из админки (`/page-seo`) имеют приоритет.
- [ ] Абсолютный `canonical` без параметров фильтров и сортировки.
- [ ] `hreflang` на все 4 языка + `x-default`, `<html lang>` по языку.
- [ ] Open Graph (`og:title/description/image/url/locale` + `og:locale:alternate`) и Twitter Card; картинка для превью абсолютная, 1200×630.
- [ ] JSON-LD:
  - на всех страницах: `Organization` и `WebSite`;
  - на всех детальных страницах: `BreadcrumbList`;
  - отели: `LodgingBusiness` + `AggregateRating` + `Review`;
  - туры: `TouristTrip` + `Offer` (цена, валюта KGS, даты) — **сейчас нет**;
  - гиды: `Person` / `LocalBusiness` — **сейчас нет**;
  - маршруты: `TouristAttraction` с `geo` — **сейчас нет**;
  - блог и гайды: `BlogPosting` / `Article` с автором и датами;
  - галерея: `ImageGallery`.
- [ ] `robots`: `noindex` для личных страниц, для страниц с фильтрами — `noindex, follow`.

**Технические требования**
- [ ] Правильные HTTP-статусы с сервера: 404 для несуществующего slug (сейчас это проверить отдельно), 301 для нормализации слэша на конце и для `www` → apex.
- [ ] `sitemap.xml` как индекс по типам (страницы, туры, отели, гиды, маршруты, выходы, блог, гайды) с `lastmod` и `xhtml:link hreflang`; `robots.txt` со ссылкой на sitemap. Оба отдаёт SSR-сервер, логика переносится из `server/routes/sitemap.xml.ts` и расширяется.
- [ ] Staging: `Disallow: /` и заголовок `X-Robots-Tag: noindex` (сейчас только robots).
- [ ] Пагинация каталогов ссылками `?page=N` с `canonical` на саму страницу. «Показать ещё» остаётся для людей, но поверх ссылок.
- [ ] Изображения через `NgOptimizedImage`: загрузчик под R2, `width`/`height`, `priority` для LCP-картинки, `srcset`, осмысленный `alt`.

**Производительность (Core Web Vitals, проверяет Lighthouse CI)**
- [ ] LCP < 2,5 с, INP < 200 мс, CLS < 0,1 на мобильном профиле.
- [ ] Карта, отзывы, виджет брони, графики, редактор — внутри `@defer` с `hydrate on viewport` / `on interaction`.
- [ ] Ленивые маршруты, бюджеты бандла в `angular.json`, инлайн критического CSS, предзагрузка шрифтов.

## 5. Стратегия: постепенная замена по URL (strangler)

Оба приложения работают одновременно на одном домене. nginx отдаёт уже перенесённые пути новому Angular-приложению, остальные — Nuxt. Cookie общие (тот же домен), поэтому вход сохраняется при переходах между частями. Переход между приложениями — обычная полная загрузка страницы.

- **Staging целиком на Angular:** на `test.ermekten.com` и `test.admin.ermekten.com` работают `apps/site` и `apps/panel` вместо Nuxt (решение от 14.10.2026), всегда с `noindex`. Неперенесённых разделов на staging нет, пока их не перенесёт своя волна; Nuxt остаётся только в проде.
- В nginx маршрутизация идёт по префиксу с учётом языка: `^/(ky/|en/|de/)?tours`. Ассеты Angular (`main-*.js`, `chunk-*.js`, `styles-*.css`) направляются в новый контейнер, у Nuxt остаётся `/_nuxt/`.
- Перед переключением каждой волны на проде:
  - **сравнение обхода:** скрипт проходит по sitemap обоих сайтов и сравнивает статус, title, description, canonical, hreflang и JSON-LD;
  - **Lighthouse CI** проходит по бюджетам;
  - **ручная проверка в Telegram Mini App.**
- После переключения 1–2 недели следим за Search Console (покрытие, ошибки, CWV). Откат — одна строка в nginx.

## 9. Трек Б: Telegram-бот на Go (Telego)

**Сейчас:** `apps/bot` — NestJS + Telegraf, ~630 строк. Работает через long polling, своей базы нет; аккаунты, привязка Telegram и контакты поддержки берутся из `users` по gRPC.

**Станет:** `services/bot` — отдельный Go-сервис в своём Docker-контейнере (`services/bot/Dockerfile`, образ `ermekten-bot`, сервис `bot` в `docker-compose*.yml`). Построен на [Telego](https://github.com/mymmrac/telego) (последняя версия на 14.10.2026 — v1.12.1):
- типизированный клиент Bot API — пакет `telego`;
- маршрутизация обновлений с предикатами и middleware — пакет `telegohandler`;
- клавиатуры и сообщения — пакет `telegoutil`.

**Структура** — по правилам остальных Go-сервисов, но с Telego вместо Gin, потому что HTTP API у бота нет:
- `cmd/bot/main.go`;
- `internal/config` — конфиг через `services/pkg/config`;
- `internal/handlers` — обработчики Telego;
- `internal/keyboards` — клавиатуры;
- `internal/session` — сессии редактирования профиля;
- `internal/usersclient` — либо общий `services/pkg/usersclient`, расширенный нужными методами.

**Общие правила сервиса:**
- логи через `services/pkg/logger` (slog);
- gRPC-клиент из уже сгенерированного `services/proto/gen/go/users/v1`;
- свой Go-модуль с `replace` на `pkg`, сборка с `GOWORK=off`.

**Получение обновлений:**
- **Long polling** (`UpdatesViaLongPolling`), как и сейчас. Публичный URL не нужен, gateway и nginx не меняются, локально работает так же, как в проде. Для одного экземпляра бота этого достаточно.
- **Вебхук Telego** (`UpdatesViaWebhook` с секретным токеном) — на будущее, если понадобится несколько экземпляров или меньшая задержка. Тогда добавится маршрут через gateway/nginx.
- При старте бот вызывает `setChatMenuButton` (кнопка Mini App, URL из `MINI_APP_URL`).
- Корректная остановка по SIGTERM: дождаться обработки текущих обновлений.

**Переменные окружения** остаются прежними: `BOT_TOKEN`, `USERS_GRPC_ADDR`, `MINI_APP_URL`. `USERS_PROTO_PATH` больше не нужен — Go-клиент собран из сгенерированного кода. Секреты в GitHub не меняются.

**Уведомления из `trails` и `payments`** продолжают уходить через `services/pkg/telegram`: им нужен только `sendMessage`. Перевод их на Telego — отдельное решение, не входящее в этот трек.

**Что переносится один в один (паритет):**

| Сценарий | Источник в `apps/bot` | Обработчик Telego | gRPC |
|---|---|---|---|
| `/start`: приветствие, главное меню, кнопка Mini App, создание аккаунта | `onStart` | `th.CommandEqual("start")` | `UpsertTelegramUser` |
| `/start verify_<token>`: подтверждение регистрации по телефону | `handleVerificationDeepLink` | тот же, разбор аргумента команды | `ConfirmTelegramVerification` |
| `/start link_<token>`, кнопки `link_move:*` / `link_cancel`: привязка Telegram к аккаунту сайта | `handleLink`, `onLinkMove`, `onLinkCancel` | `th.CallbackDataPrefix("link_move:")`, `th.CallbackDataEqual("link_cancel")` | `LinkTelegram` |
| Кнопка «Профиль» и редактирование имени и телефона, включая ошибку «телефон занят» | `onProfile`, `profile_edit_*`, `onText` | `th.TextEqual(...)`, `th.CallbackDataPrefix("profile_edit_")`, `th.AnyMessageWithText()` | `GetUser`, `UpdateProfile` |
| Кнопка «Поддержка» | `onSupport` | `th.TextEqual(...)` | `GetSupportInfo` |

Тексты сообщений, подписи кнопок и `callback_data` копируются без изменений: пользователи и ссылки с сайта (`t.me/<bot>?start=…`) не должны ничего заметить. Сессии редактирования профиля остаются в памяти, с TTL 10 минут.
